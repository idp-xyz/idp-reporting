# 单据 PDF 引擎对比：Typst 与 Go 自研版式（fpdf）

## 验收阈值（在运行对比之前写下并提交）

两个引擎使用同一套检查（spikes/pdfeval/eval.py）、同一份生成数据和同样的单据要素。同样的参数下，两个程序生成的数据文件必须逐字节一致，否则对比无效。

硬性阈值（任何一项不满足即不合格）：

| 编号 | 要求 |
|---|---|
| H1 | 正确性：所有规模下每行恰好出现一次、顺序正确；每页都有表头和"第 X 页 / 共 Y 页"；每页的承前页、过次页金额与独立重算一致；末页的合计和人民币大写正确 |
| H2 | 不静默丢数据：所有摘要文字都完整、原样出现在 PDF 中，包括比一页还高的行。如果做不到，必须拒绝渲染 |
| H3 | 恶意字符串按原样显示，不被执行 |
| H4 | GB/T 15834 避头尾：压力测试 0 违例 |
| H5 | veraPDF PDF/A-2b 通过；不开 PDF/A 的对照版本不通过 |
| H6 | 同一输入两次输出逐字节一致 |
| H7 | 只嵌入指定字体，中文可以复制和搜索 |

暂定阈值（业务的页数分布、并发和内存预算尚未提供，数值待确认）：

| 编号 | 要求 |
|---|---|
| P1 | 约 1000 页单据的峰值内存 ≤ 1GB |
| P2 | 约 1000 页单据的耗时中位数 ≤ 10 秒（重复 5 次） |
| P3 | 4 路并发渲染约 100 页单据，全部成功 |

另外记录但不设阈值：开发量（代码行数、需要自己实现的能力）、运行时依赖、沙箱要求、文件大小。

## 结果

2026-10-27。fpdf：codeberg.org/go-pdf/fpdf v0.12.0；Typst：0.15.1。两份结果出自同一版检查脚本，原始数据在 results/fpdf/results.json 和 results/typst/results.json。同样的参数下，两个程序生成的数据文件逐字节一致（已核对）。

| 阈值 | fpdf 自研 | Typst |
|---|---|---|
| H1 正确性（5 / 150 / 400 / 3000 / 30000 行） | 通过 | 通过 |
| **H2 不静默丢数据** | **通过**：超高行跨页拆开，120 句全部显示 | **不通过**：渲染成功且无警告，只显示 38/120 句 |
| H3 恶意字符串 | 通过 | 通过 |
| H4 避头尾（压力测试） | 通过，0/1448 行 | 通过，0/1608 行 |
| H5 PDF/A-2b（veraPDF，含反向对照） | 通过。前提是修复 fpdf 的两个文件尾缺陷（见下） | 通过 |
| H6 确定性 | 通过 | 通过 |
| H7 字体、可搜索、元数据可读 | 通过。子集字体名缺少标签前缀，不在阈值内 | 通过 |
| P1 约 1000 页峰值内存 ≤ 1GB（暂定） | 通过：202MB（30000 行、1053 页） | 不通过：2.70GB（30000 行、831 页） |
| P2 约 1000 页耗时中位数 ≤ 10 秒（暂定） | 通过：0.36 秒（0.34–0.40） | 勉强通过：8.73 秒（8.55–9.79） |
| P3 4 路并发 3000 行 | 通过：0.13 秒，峰值合计 1.0GB | 通过：1.02 秒，峰值合计 1.2GB |

只记录、不设阈值的项：

| 项目 | fpdf 自研 | Typst |
|---|---|---|
| 约 1000 页的文件大小 | 3.5MB | 33.5MB |
| 1 页单据的峰值内存 | 153MB（每个进程都要解析两个约 10MB 的 TrueType 字体；常驻服务只需解析一次，但这一点未实测） | 39MB |
| 代码量（非空行） | 版式 193、绘制 245、主程序 81，共 519；另有测试 102 | 模板 63、调用封装 126，共 189 |
| 运行时依赖 | 进程内的 Go 库，没有外部进程 | 56MB 的外部二进制，需要断网命名空间、超时和内存限制 |
| 模板安全 | 不适用：没有模板语言，版式就是 Go 代码 | 需要沙箱（见 spikes/typst/REPORT.md） |

**按事先定的阈值，fpdf 自研方案全部达标，Typst 方案未通过 H2 和 P1。** 结论与选择 Go 自研的方向一致。

## fpdf 方案的已知问题和代价

- **fpdf v0.12.0 有两个上游缺陷，已在文件尾后处理中修复。** 一是用了 OutputIntent 后，文件尾的 `/Info` 指向 ICC 数据流，所有阅读器都读不到标题、作者和日期。这一点 **veraPDF 没有发现**，是元数据检查抓到的。二是不写 `/ID`。后处理只改文件尾，修正前会核实目标对象确实是文档信息字典。生产上应该向上游提交修复，或者 fork 后附带回归测试。
- 子集字体名没有 ISO 32000 要求的 6 位标签前缀。
- 只支持 TrueType 字体，需要从官方可变字体实例化出静态 TTF。
- **排版细节要自己实现。** Typst 自带行首标点挤压、中英文间距，省略号处理也更好。fpdf 方案目前只有避头尾、破折号和省略号不拆开、间隔号随前字这几项；标点挤压、续行"续"字标记、合并单元格、图片、条码、分组小计都还要写。代码量已经是 Typst 方案的 2.7 倍，后续还会增长。

## 对比的局限

- 两边用的字体文件不同：Typst 用官方的 CFF OTF，fpdf 用从官方可变字体实例化的 TTF。版面也不完全相同，所以同样 30000 行，Typst 排成 831 页、fpdf 排成 1053 页。按每页内存算，差距约 17 倍（3.25MB 对 0.19MB），结论不变。
- Typst 的 H2 失败针对的是"行不可跨页"的模板写法。允许行跨页的写法未测，Typst 在那种写法下是否完整未知。
- 数据是合成的；P1–P3 的阈值是暂定值；只在一台机器上测；版面美观只由一个人目测；**本对比没有经过独立审查**。
- 检查脚本在运行中修正过一次：Typst 会挤掉行首左引号前的半个空白，导致行首左移 4.5 磅，最初 1.5 磅的容差因此误报"文字不完整"。改为 5.4 磅后，两边都用修正后的同一版重跑。修正后 Typst 的超高行截断仍被检出。

## 独立审查后的更正（2026-10-27）

两位审查者分别从"方法与结论"和"fpdf 代码"两个方向独立审查了本对比。两人都独立复现了上面的数字（数据逐字节一致，正确性字段一致，性能在噪声范围内），并确认检查能够失败。他们的发现推翻了上面的部分结论，更正如下。

### 1. Typst 的 H2 失败来自模板写法，不是 Typst 本身

模板写了 `#set table.cell(breakable: false)`，而 fpdf 方案实现了"超高行跨页拆开"的对策，Typst 没有用上它自带的同类对策。改成 `breakable: true` 后，用同一版检查重跑（results/typst-breakable/results.json）：超高行 120/120 完整，**H1–H7 全部通过**，veraPDF 通过且对照不通过，输出确定。代价是普通行也可能在页底被拆开（压力测试从 32 页变为 31 页），而 fpdf 只在行高于一页时才拆。spikes/typst/statement.typ 已改为可拆行。

| 项目 | fpdf 自研 | Typst（可拆行） |
|---|---|---|
| H1–H7 | 全部通过（仅限测试数据，见第 3 条） | 全部通过 |
| 30000 行峰值内存 | 202MB（1053 页） | 2788MB（831 页） |
| 30000 行耗时中位数 | 0.36 秒（1053 页） | 9.39 秒（831 页，5 次中 8.89–10.93） |
| 按每 1000 页折算的耗时 | 0.34 秒 | 11.3 秒 |
| 每多一页的内存增量（审查者测算） | 约 0.046MB | 约 3.21MB（约 70 倍） |

前文"Typst 未通过 H2"的说法**作废**。

### 2. 阈值并不是盲定的

阈值提交于 316dd99，确实早于对比结果，事后也没有改动。但提交时作者已经知道：Typst 会截断（cac2738）；Typst 在 831 页时用了 2.70GB、8.4–9.3 秒，并且报告里写过"约 300 页 ≈ 1GB"（3aa92b2）；fpdf 筛选时 831 页 0.25 秒、98MB（97b0e75）。P1 的 1GB 和 P2 的 10 秒都是参照 Typst 的已知数据定的，所以"先定阈值"在这里**起不到防偏差的作用**。另外 P2 没有像 P1 那样按页数折算；折算后 Typst 为 11.3 秒/千页，也不通过。H7 在结果表里加入了"元数据可读"，同时把子集字体名前缀排除在外，这两处事后调整都只涉及 fpdf。

### 3. fpdf 方案作为生产代码不合格

代码审查结论：版式与精确算术的核心是可靠的（30 万随机字符串加 4500 万次模糊测试，没有丢字或乱序；人民币大写 50 万个值全部正确）。但输入处理不合格：
- **阻塞问题**：基本平面以外的任何字符都会让 fpdf 在 `Output` 时越界，进程直接崩溃。这包括 Noto Sans SC 已收录的 445 个此类字符，例如 𬌗（U+2C317）。截断的 UTF-8 也会崩溃。原因是 fpdf 的 UTF-8 字体映射只覆盖基本平面，修复需要改动库的核心部分。
- **重大问题**：字库没有的字和换行符会被静默画成空框（.notdef）；非法 UTF-8 会被替换成别的字；超长的单据号会把摘要列挤出页面；单位名和客户名过长时会重叠；标题超过约 44 个汉字会超出页面。
- **次要问题**：页面主体比一行还矮时分页会死循环；超长金额会跨行甚至跨页；折行有少量边界瑕疵；XMP 和 Info 对控制字符的处理不一致；没有任何输入上限（违反 CODING_STANDARDS.md）。

检查脚本没有发现这些问题，因为测试数据里没有这类字符或超长值，脚本也没有"文字重叠"类的版面检查。

### 4. 字库覆盖问题对两个引擎都存在

只用 Noto Sans SC 时实测：
- 𬌗（基本平面外，字库有）：Typst 正确渲染，fpdf 崩溃。
- 𠮷（U+20BB7，字库没有，人名和店名中会出现）：**Typst 静默丢掉这个字，且没有任何警告**；fpdf 崩溃。
- emoji、泰文（字库没有）：两者都画不出字形。

所以无论选哪个引擎，都必须在 Go 侧渲染前检查每个字符是否被字库覆盖，没有覆盖就拒绝或者走回退字体，不能交给引擎处理。

### 更正后的结论

两个方案在测试数据上都满足全部硬阈值，都还不能直接上生产。真正的差别是：
- **fpdf**：内存和速度大幅领先，进程内运行，没有模板语言带来的攻击面。但它不支持基本平面以外的字符（这是库本身的限制，要修就得 fork 核心部分），而且输入稳健性、版面防溢出、排版细节都要自己补，代码量还会继续增长。
- **Typst**：支持完整 Unicode，排版能力更强，代码量约为 fpdf 方案的三分之一，运行在独立进程里，崩溃、超时和内存超限都由操作系统隔离。但内存约是 fpdf 的 70 倍，要做断网沙箱和资源限制，版本处于 0.x，升级可能改变分页。

选哪个取决于还没有拿到的业务数据：单据的页数分布、并发量和内存预算，以及是否必须支持基本平面以外的汉字（例如 GB18030-2022 的符合性要求，具体级别待核实）。

## 补充：pdfme（2026-10-27）

为回答"pdfme 是否可行"做了一次实测，探针和结果在 spikes/pdfme/。实测对象是 @pdfme/generator 6.2.8（MIT，2026-10-21 发布），运行在 Node 24.22.0 上；数据文件与上面 fpdf、Typst 的运行相同，字体为 Noto Sans SC。这次只用同一套规则做了部分检查，没有跑完整的 eval.py，也没有经过独立审查。

| 项目 | 结果 |
|---|---|
| 150 行样例 | 6 页；行齐全且有序；每页都有表头和"第 X 页 / 共 Y 页"；摘要完整、原样；251 行摘要 0 条避头尾违例；只嵌入 Noto 子集；中文可搜索 |
| 比一页还高的行 | **静默截断**：渲染成功、没有警告，120 句只显示 2 句 |
| 字符 | 基本平面外、字库有的字（𬌗）能渲染；字库没有的字（𠮷、emoji）在文本层变成 `\x00`，即静默丢失 |
| PDF/A-2b（veraPDF） | **不通过**：它 fork 的 pdf-lib 没有 OutputIntent 和 PDF/A 标识，需要自己写底层后处理 |
| 确定性 | 否：创建和修改时间都是渲染时刻（可以修） |
| 承前页 / 过次页 | 每页能变化的内容只有 {currentPage}/{totalPages}，需要自己写插件（未评估） |
| 30000 行 | 1159 页，26.2 秒，峰值 2.1GB（Node 进程，1 页时就有约 380MB） |
| 设计器 | @pdfme/ui 依赖 React 19 和 antd 6（解压后 22.6MB）；我们的控制台是不打包的纯 HTML/JS，CSP 只允许 `script-src 'self'` |
| 依赖 | @pdfme/generator 对 @pdfme/pdf-lib 的版本要求是 `*`，peer 依赖是 `latest`，只能靠锁文件固定 |

结论：pdfme 的长处是现成的所见即所得设计器，模板是 JSON 数据而不是代码，适合标签、证书、套打这类单页固定版式的表单。对本平台的多页对账单和报表，它在超高行截断、PDF/A、承前过次三项硬要求上都不满足，大文档性能也是三者中最差的。它不适合做主引擎；如果以后出现"套打或固定表单"的需求，可以单独考虑。
