# 真实产品只读报表接入合同（S02 工作稿）

状态：待来源产品确认与实现；不是已经部署的 API。沿用 docs/s00/INTERFACES.md
四个操作与现有 Go Adapter，不引入产品私有包或从平台跨库执行产品 SQL。

S19-A 起，来源产品**不再需要平台为它写 Go 适配器**：产品在自己的服务里实现固定的
HTTPS 协议——报表来源协议第 1 版（docs/SOURCE_HTTP_PROTOCOL.md，机器可读的
docs/source-openapi.json），平台用已发行、已审查的通用适配器 `http` 接入
（docs/DEPLOYMENT.md“Connecting a source product over HTTP”）。协议把下面四个操作
（及可选的出具授权）原样搬到 JSON over HTTPS：每个请求都显式带来源上下文
（平台租户、issuer、subject、integration、source tenant），产品在服务端把
subject 映射为自己的 actor，除此之外请求里的任何东西都不能作为授权依据；
错误是封闭的错误码集合；数值一律是精确字符串。产品实现后，用
`reporting-source-check`（协议第 7 节）对平台将要连接的端点自检，全部通过才配置连接。
`adapters/httpsource/sourcetest` 是协议的 Go 参考实现。

| 保留结果（可选能力，ADR 0026，S25-B2） | 产品是否为读取的范围担保：读取本身过期之后（`expires_at`，至多 15 分钟），在 `scope_expires_at` 之前继续按当时的权限回答 `authorize`，平台才能把导出文件、定时报表的数据与正式出具的文件保留到读取之后（docs/SOURCE_HTTP_PROTOCOL.md "The scope a source vouches for"）。须说明：担保多久（正式出具的文件要保留满 `retention.issued`，担保就不能短于它）；靠什么回答（按读取存的记录，还是自描述的 `scope_handle`），存多少、存多久；只按自己的记录判断到期，不看请求带回的时间；停止担保之后，对已经担保过的读取仍要回答到各自到期。详见下文“为读取范围担保的产品”。不打算担保的产品，连接上不要声明 `kept_results: true`，一切照旧：结果随读取结束。打算担保的产品，先在测试环境担保并通过 `reporting-source-check -kept-results`（规则 K1–K2）、交付产品自己的测试结果，运营方再声明，然后产品才在平台连接的端点上开始担保（次序见下文） |
| 服务身份 | 平台到来源的连接凭据（协议第 1 节：Bearer 服务凭据和/或 mTLS 客户端证书，CA 由平台固定）、真实委托主体及用途/受众；机器账号不能自动代表任意用户——服务凭据只证明“这是平台”，代表谁只看请求里的 context，由产品自己映射与授权 |
| 对账 | 匿名化但可复核样本、来源独立总量/金额、负值/大数/多件/跨日/取消及权限边界案例 |

## 操作义务

DescribeCatalog 仅返回当前主体可访问的已发布版本与批准组合，不接受客户端
SQL/任意公式。PrepareRead 在来源可信事务中验证身份映射、当前权利与查询，
返回绑定 source tenant、platform owner、integration、query hash、数据集版本、
watermark、原始授权范围及 expires_at 的稳定读取引用。ReadPage 仅沿同一引用
投影；当前数据变化不得让后续页跳到另一个版本。AuthorizeCurrent 比较当前
权利对原范围的完整覆盖；扩权不能扩大旧结果，缩权不能只过滤文件后放行。

不能以不透明策略 hash 相同代替范围覆盖证明。来源应将权限、来源不可用、
过期、参数不支持及损坏区分；平台仍关闭披露。网络超时、授权缓存最大年龄、
重试/撤权竞态与远程快照配额必须在真实合同中确定，不预造跨系统原子性。

平台排队任务保存可信 owner 与原范围，不能把用户 Bearer JWT 写入任务、快照
或文件。任务在用户令牌过期后能否继续执行取决于当前来源资格；读取任务、
分页与下载仍需新的有效请求认证及来源当前授权，不将提交时验签替代以后读权。

## 为读取范围担保的产品（保留结果，ADR 0026，S25-B2）

可选能力。产品在 `reads` 的回答里多给一个时间 `scope_expires_at`，就是担保：在这个时间之前，即使读取本身已经过期、
分页不再提供，产品仍然回答 `authorize`。平台据此把由这次读取做出的结果保留到读取之后——导出文件与定时报表的数据保留
`retention.results`（默认 7 天），正式出具的文件保留 `retention.issued`（默认 10 年），都不超过担保的时间——并且每次下载、
每页数据之前仍然询问产品。不担保的产品一切照旧：结果随读取结束。

产品必须做到：

1. 担保期内 `authorize` 的规则与读取有效期内完全相同：当时的权限覆盖冻结时的整个范围（每个公司、读取所依据的每一行、时区、
   币种政策）才回答 `authorized: true`；扩权不扩大旧读取，缩权即拒绝；权限源不可用回答 `unavailable`，不得放行。
   在产品里撤销一个人的权限，他此前保留在平台上的每一份文件的下一次下载就被拒绝。
2. 自己保存到期时间与冻结的授权范围：按读取存一条记录，或者用一个自描述、且能验证确由自己签发的 `scope_handle`。
   读取过期之后不必再保留冻结的数据版本。
3. **只按自己的记录判断范围是否到期，绝不按请求带回的 `scope_expires_at`。**带回的读取若这个时间与当初不同，或者没有了，
   就不是产品做出的读取，回答 `denied`（与 watermark 被改一样）。自己的记录到期之后拒绝（`expired` 或 `denied`），
   不论请求怎么写。
4. 需要读取本身的操作仍随 `expires_at` 结束：`pages`，以及出具的 `prepare`（它要用冻结的行核对）。
5. 产品在 `reads` 时不知道平台将怎样使用这次读取（预览什么都不保留，导出可能保留数天，正式单据保留多年），所以对每次读取
   一视同仁地担保。按读取存记录的产品要为每一次读取存到担保到期，预览的读取也在内；自描述的 handle 不需要存储。
   可以只为部分数据集担保，时间也可以不同；超过自己的上限回答 `budget`。
6. 平台保留到“读取到期 + 该类结果的保留时间”与担保时间两者中较早的一个。要让正式出具的文件保留满 `retention.issued`，
   担保就不能短于它；只担保 7 天的产品，它出具的文件在平台上也只保留 7 天。
7. 停止担保时，新的读取不再带 `scope_expires_at`，但已经担保过的读取仍要回答，直到各自的担保到期；忘掉它们，
   平台上由它们做出的每一份保留文件都会被拒绝。

接入次序（docs/DEPLOYMENT.md “Keeping results: the order”）。平台是否把产品的数据保留到读取之后，由运营方在连接上声明，
不由来源的回答开启：连接没有声明时，带担保的读取会被整个拒绝（`INTEGRITY_FAILURE`，预览也在内）。所以：

1. 产品先在**测试环境**担保，在那里通过 `reporting-source-check -kept-results`，并完成下面“自己的测试”。
   平台连接的端点此时还不担保。
2. 运营方在连接上声明 `kept_results: true`，逐台重启服务器。此时什么都不变。
3. 产品在平台连接的端点上开始担保。此后可以对这个端点再跑一次 `reporting-source-check -kept-results`（只读）。

关闭时反过来：产品先停止为新读取担保，运营方再去掉声明。次序反了，带担保的读取被拒绝，直到次序恢复；不会有任何未声明的保留。

`reporting-source-check -kept-results`（规则 K1–K2，只读；端点必须已经担保，否则 K1 不通过）：K1 样本读取带有晚于
`expires_at` 的 `scope_expires_at`；K2 原样带回的读取被授权，换一个到期时间或去掉它即被拒绝，之后原样的读取再次被授权
（证明那两次拒绝不是因为读取恰好到期）。不带这个参数检查一个已经担保的端点，会在 R1 失败并说明原因。

**检查器看不到承诺本身**：读取过期之后产品是否继续回答、是否按当时的权限回答、担保到期之后是否拒绝。读取最长 15 分钟，
担保可能长达数年，几分钟的检查无法等待。产品必须用**自己的测试**证明以下各条——在可以拨动的时钟上，或者把自己记录里的
时间改到过去——并把结果交给平台方（上线清单第 20 项）：

1. 读取过期之后、担保期内：`pages` 与 `prepare` 被拒绝，`authorize` 仍回答是。
2. 此时撤权即拒绝；缩小范围即拒绝；恢复冻结时的权限再次回答是；权限源不可用回答 `unavailable`。
3. 带回的读取改了 `scope_expires_at`，或去掉了它：拒绝（`denied`）。
4. 担保到期之后：拒绝，无论权限如何。
5. 产品进程重启之后，此前的担保仍然有效（记录是持久的，或 handle 可验证）。

平台自带的两个模拟器各有一份这样的测试，可作样板。内存模拟器在测试拨动的时钟上，覆盖第 1 至 4 条（它没有可重启的进程）：
`adapters/contractsim` 的 `TestTheSimulatorServesPagesWhileTheReadLastsAndAuthorizesWhileTheScopeDoes`。持久模拟器不拨时钟，
而是把自己记录里的时间改到过去，由数据库时钟判断，五条都覆盖，含重新打开：`adapters/contractsim/pgsource` 的场景
`a_read_serves_its_pages_while_it_lasts_and_is_authorized_while_its_scope_does`。

## 两个产品的首批对账约束

Brant 应收账龄须由真实未清项及核销/贷项语义产生，不能把核价/报价金额当应收。
账龄基准日期、到期日、未来日、核销截止、冻结水位、币种换算与四舍五入都由
来源发布版本化口径。未提供时不发布 receivables.aging 的真实目录。

Parcel 须分别声明运单头与物理件；一票多件不能放大头表金额。创建、确认、
交接、签收的计数分别定义，状态版本映射、时区日界、重复事件、取消/退件
及补差入账语义由来源确定。display_amount_minor 是成交快照，不自动等于
净收入、已收款或成本。新增报表指标 ID 与公式须经产品确认，不直接沿用 mock。

## 验收次序

1. 固定真实提交、身份/委托及数据合同；将上表未知项逐项变为可执行样本。
2. 来源侧按 docs/SOURCE_HTTP_PROTOCOL.md 实现四个只读操作（出具时再加三个出具路由；要让平台能申请作废，再加作废路由；要让平台把结果保留到读取之后，读取再带 `scope_expires_at` 并在担保期内继续回答 `authorize`），来源自己的权限与事务设施继续权威。
3. 产品方用 `reporting-source-check` 对预发端点全部通过（用平台将使用的凭据与 CA；`-issue` 与 `-cancellation` 只在非生产端点上跑；担保范围的产品加 `-kept-results`，并交付“为读取范围担保的产品”一节要求的自己的测试结果）。
4. 平台配置 `"adapter": "http"` 的连接并验证 owner、source tenant、版本/水位/TTL 的完整绑定（上线清单第 17 项）。
5. 在两个产品各完成目录、预览、任务、分页、XLSX、撤权/故障与独立业务对账。
6. 再更新 I14–I16 的资格；生产部署与容量准入另行按既定阶段验收。
